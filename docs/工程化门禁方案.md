# AIDS 工程化门禁方案（防文档漂移）

> **版本**：v1.0 ｜ **定位**：流程/机制方案，非代码交付
> **解决的问题**：bysj 的病——"有 design-report skill 门禁、有 12 万字设计文档，工程化仍然薄弱"
> **选定基线**：GitHub Actions ｜ 标准档（契约测试 + pre-commit + CI + 启动断言 + ruff/pyright basic）

---

## 0. 一句话结论

**门禁必须从「输入端」移到「输出端」。**

不要求 AI 承诺"读过 PRD"，而是要求它交出的代码**能通过契约测试**。
文档管「为什么」，测试管「必须」。凡是能用代码检查的，绝不用文档要求。

---

## 1. 病根溯源：bysj 为什么坏

| 环节 | bysj 做法 | 失效机理 |
|---|---|---|
| 门禁位置 | skill 强制"编码前读设计报告" | 「读过」无法验证 → 形式合规；读了 ≠ 对齐 |
| 管什么 | 设计报告管「做什么功能」 | 工程化是「怎么做才不出事」，不在功能规格内 |
| 谁负责 | 无归属 | CI/容器/lock/测试隔离不属任何功能子任务，没人排期就不存在 |
| AI 注意力 | 局部显式需求 ≫ 全局隐式非功能 | 上下文里 F1-F10 显眼，§7 一句"测试别连生产库"必被淹没 |
| 厚文档 | 12 万字，单次塞不下 | 跨章节一致性必漏（改一半，另一半没改） |

### 铁证（决定方案形态的关键观察）

同一优先级的两条约束，在 bysj 里的结局截然相反：

| 约束 | 载体 | 结局 |
|---|---|---|
| RAG 必须隔离测试库 | **代码护栏** `_require_isolated_db()` | ✅ 永久生效 |
| "测试别连生产库" | **文档一句话** | ❌ MySQL 侧至今未隔离 |

**结论**：写成代码的 100% 生效，写成文档的概率衰减。
→ 所以本方案的全部设计都围绕一件事：**把文档事实翻译成可执行断言。**

## 2. 三层防线总览

```
┌─────────────────────────────────────────────────────────┐
│  第一层  契约即代码                                       │
│  把文档里的"事实"变成 pytest 断言 —— 跑不通就红             │
├─────────────────────────────────────────────────────────┤
│  第二层  CI 门禁                                          │
│  pre-commit（秒级）→ CI on PR（契约+单测）→ CI on merge（冒烟）│
│  违规代码无法合并                                          │
├─────────────────────────────────────────────────────────┤
│  第三层  结构性防御                                        │
│  启动断言 / 类型系统 / 架构守卫 / 迁移可回退 / 密钥扫描       │
│  不依赖任何人的自觉                                        │
└─────────────────────────────────────────────────────────┘
```

**核心原则：单一可信源（SSOT）+ 反向生成。**
状态枚举绝不在 DDL / PRD / 代码 / 前端里各写一遍。代码里定义一次，其余全部由它生成或校验。

## 3. 第一层：契约即代码

AIDS 的文档资产非常适合机械化。下表 8 类约束全部可从「约定」升级为「测试」：

### 3.1 契约测试清单

| # | 文档事实 | 来源 | 机械化手段 | 失败即 |
|---|---|---|---|---|
| C1 | 38 张表 / 419 字段；前缀 `biz_`/`sys_`/`ai_` | `sql/schema.sql` ↔ `DATA-DICTIONARY.md` | 反射 DDL 实际表数/字段数/前缀分布，与字典声明值比对 | DDL 与字典漂移 |
| C2 | 11 组状态枚举映射（DDL 数字 ↔ PRD 英文名 ↔ 代码常量） | `DATA-DICTIONARY.md` §一 | 代码侧定义 `IntEnum`，测试逐组断言"值 ↔ 常量名"与字典表逐字一致 | 状态机错乱（"10 是待付款还是待发货"） |
| C3 | 12 条数据库不变量 | `DATA-DICTIONARY.md` §四 | 逐条配测试；应用层保证的（如库存恒等式）用事务回滚随机操作 + 断言 | 库存账不平 / 超额退款 |
| C4 | 错误码分段 `1xxxx`~`9xxxx` + 明细表 | `API.md` §1.2/1.3 | 扫描代码所有 `raise BizError(code=...)`，断言 code 在表内且段位与所属模块匹配 | 错误码野生、乱返回 10008 |
| C5 | 库存恒等式 `total = available + locked + sold` 且四段 `>= 0` | 不变量 #1/#2 | 属性测试：随机造锁定/扣减/释放序列，每次断言恒等式与下界 | 超卖（电商致命） |
| C6 | 库存流水幂等键构造规则（`LOCK:{orderNo}:{skuId}` 等 6 种） | 字典「幂等键构造规则」 | 单测 6 种键的生成函数，逐字比对格式 | 重复扣减 |
| C7 | 统一响应体 `{code,message,data}`；业务失败也返回 200 | `API.md` §1.1 | 契约测试遍历全部路由，断言响应结构 + 业务失败 HTTP=200 | 前端拦截器失配 |
| C8 | idempotent_key / channel_trade_no / order_item_id 等 UNIQUE | 不变量 #9~#12 | 反射 DDL 断言 UNIQUE 索引真实存在（防迁移漏建） | 重复发货/刷评价 |

### 3.2 关键设计：C2 状态枚举如何做 SSOT

**反面做法**（bysj 式，必坏）：

```python
# order_service.py —— 魔法数字硬编码
if order.status == 20: ...

# order_model.py —— 又一套常量
STATUS_PAID = 20

# 前端 order.js —— 第三套
const STATUS = { 20: '待发货' }
```
三套并存 → 必然漂移。

**正确做法**（单一定义 + 反向校验）：

```python
# app/domain/enums.py —— 全项目唯一权威，DDL 与 PRD 都引用它
class OrderStatus(IntEnum):
    PENDING_PAY = 10   # 与 DATA-DICTIONARY §一 逐字一致
    PAID = 20
    SHIPPED = 30
    ...
```

配套契约测试 `tests/contract/test_enum_mapping.py`：
- 解析 `DATA-DICTIONARY.md` §一的 markdown 表格 → 得到 `{值: PRD状态名}` 映射
- 与 `OrderStatus` 逐项比对，**不一致即 FAIL**
- 同时断言 DDL 列注释里的中文名与表格「DB 注释名」列一致

**收益**：文档改了枚举、代码没改 → CI 立刻红。反向漂移也被拦住。

### 3.3 契约测试放哪

```
tests/
├── contract/                 # 文档 ↔ 代码 一致性（本方案核心）
│   ├── test_schema_matches_dict.py     # C1
│   ├── test_enum_mapping.py            # C2
│   ├── test_error_codes.py             # C4
│   ├── test_response_envelope.py       # C7
│   └── test_unique_indexes.py          # C8
├── invariants/               # 业务不变量（C3/C5/C6）
│   ├── test_stock_invariant.py
│   └── test_idempotent_key.py
└── unit/ integration/ e2e/   # 常规测试
```

> `tests/contract/` 的存在本身就是"地图"——刚建时大量 FAIL，正说明文档里有多少约定尚未落地。

## 4. 第二层：CI 门禁

### 4.1 三层触发

| 层 | 触发 | 内容 | 目标耗时 |
|---|---|---|---|
| L1 | `pre-commit`（本地） | ruff format/check、残留文件 grep、错误码快速扫描、禁止提交 `.env`/密钥 | < 5s |
| L2 | PR 到 main（CI） | 契约测试 + 单元测试 + `pyright basic` + Alembic 迁移可回退检查 | < 5min |
| L3 | merge 到 main（CI） | 起 compose 最小档（3 服务）→ 跑关键链路冒烟（登录 → 下单 → 支付回调） | < 15min |

### 4.2 GitHub Actions 结构（示意）

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push: { branches: [main] }

jobs:
  lint:
    steps: [ruff format --check, ruff check, 残留 grep]
  contract:                     # ← 本方案的核心，PR 必过
    steps:
      - 起 MySQL8 + Redis（services）
      - alembic upgrade head     # 真实建表
      - pytest tests/contract -x
      - pytest tests/invariants
  typecheck:
    steps: [pyright]
  smoke:                        # 仅 main 分支
    if: github.ref == 'refs/heads/main'
    steps: [docker compose up 最小档, bash deploy/smoke.sh]
```

**关键点**：`contract` job 必须跑在**真实 MySQL 8** 上（不是 SQLite），因为 C1/C8 依赖 MySQL 特有的 `CHECK`/`ngram` 全文索引/`UNIQUE` 语义。用 `services:` 起官方镜像即可。

### 4.3 把「读文档」替换成「过检查」

| | bysj 做法 | 本方案 |
|---|---|---|
| 约束对象 | 输入（读没读） | **输出（对不对）** |
| 验证方式 | 无法验证 | `pytest tests/contract` 绿/红 |
| 兜底 | 靠自觉 | 靠 CI 拦截合并不通过 |

## 5. 第三层：结构性防御

不依赖任何人的自觉，由运行时/类型系统强制。

| # | 机制 | 实现 | 拦住什么 |
|---|---|---|---|
| S1 | **启动断言** | `APP_ENV=production` 时：DB 名含 `test`/`dev` → `sys.exit(1)`；`SECRET_KEY` 为默认值 → 退出；`ARK_API_KEY` 缺失 → 退出 | 测试连生产库（bysj 的老病，用代码根治） |
| S2 | **类型系统** | `pyright` basic；接口层强制 Pydantic v2 模型，禁止裸 `dict` 出入参 | 隐式 None、字段拼错 |
| S3 | **架构守卫** | 自写 pytest / `import-linter`：API 层不得直接 import ORM Session；模块间不得跨域直读对方表 | 分层腐化 |
| S4 | **数据权限守卫**（对应 PRD §2.2 / TASKS BE-04） | Repository 基类统一注入 `WHERE user_id=?`；**测试扫描代码，禁止 `request` 参数直接取 userId 做权限判断** | IDOR（电商最高频漏洞） |
| S5 | **迁移可回退** | CI 检查每个 Alembic revision 必须实现 `downgrade()`，并实际执行 `upgrade→downgrade→upgrade` | 无法回滚的迁移 |
| S6 | **密钥扫描** | pre-commit `gitleaks` + CI 扫历史提交 | 密钥入库（AES Key / Ark Key / DB 密码） |
| S7 | **.gitignore 硬防** | `.env`、`*.db`、`_backup_*`、`uploads/`、`data/` | 本地配置/数据误提交 |
| S8 | **可观测性基线** | 断言 `X-Trace-Id` 全链路透传（Nginx→主业务→AI/Mock）；结构化日志含 traceId | 出事无法定位（AIDS PRD §4 已有要求） |

### S3/S4 的额外价值

TASKS BE-04 的验收标准已经写得很硬：

> **验收：用 A 的 Token 访问 B 的订单/地址/优惠券/会话全部 403，批量递增 ID 扫描无一条越权数据泄露**

这条本身就是**可自动化的**——直接写成 pytest 用例，遍历所有资源类型 + 递增 ID 扫描。文档里写"必须这样"，测试里写"不这样就把你拦下来"。

## 6. 落地顺序（贴 AIDS 梯次）

AIDS 现在 0 行业务代码，**是打地基成本最低的时刻**。等写完 3 万行再补就晚了。

```
T0 尾 / T1 初（必须先做，成本最低）
  ├─ repo 骨架 + .pre-commit-config.yaml + .github/workflows/ci.yml
  ├─ app/domain/enums.py（状态枚举 SSOT）← 对齐 DATA-DICTIONARY §一
  ├─ app/core/errors.py（错误码常量）    ← 对齐 API.md §1.2/1.3
  ├─ app/core/response.py（统一响应）    ← 对齐 API.md §1.1
  └─ tests/contract/test_{enum_mapping,error_codes,response_envelope}.py
     → 初次运行大量 FAIL，这正是"文档里有多少约定没落地"的地图

T1（随 BE-01~BE-06 推进）
  ├─ tests/contract/test_schema_matches_dict.py  ← BE-02 建表后立即可跑
  ├─ S2 pyright + S1 启动断言                    ← BE-01 起
  ├─ S4 IDOR 契约测试                            ← BE-04 同步写
  └─ CI `contract` job 上线，PR 必过

T3（交易主链路，风险最高）
  ├─ tests/invariants/test_stock_invariant.py    ← BE-11 同步写（库存恒等式）
  ├─ tests/invariants/test_idempotent_key.py     ← BE-36 对账任务
  └─ C5 属性测试（随机操作序列压恒等式）

T6 上线前
  ├─ S3 架构守卫 + S5 迁移可回退 + S6 密钥扫描
  └─ L3 冒烟 job（compose 最小档 + 关键链路）
```

### 与 TASKS 的接口

本方案不新增功能任务，而是**给现有任务挂"机械验收"**。建议在 TASKS.md 的 T1 段落补一行：

| 编号 | 板块 | 任务 | 内容与验收标准 | 依赖 |
|---|---|---|---|---|
| BE-00 | 工程 | **门禁与契约测试基线** | pre-commit + GitHub Actions CI + `tests/contract/` 五类一致性测试 + 启动断言（详见 `docs/工程化门禁方案.md`）；验收：`pytest tests/contract` 全绿且 CI 拦截一次人为违规 | DEP-01 |

> 把门禁**显式列为一个任务**，是防止它重演 bysj 悲剧的最关键一步——
> bysj 的 CI/容器/lock 之所以没有，正是因为"没人把它排进任务清单"。

## 7. 成本与收益

| 项 | 投入 | 收益 |
|---|---|---|
| 契约测试（C1-C8） | 约 2-3 天（一次性） | 文档↔代码漂移从"上线后炸"提前到"commit 时红" |
| pre-commit + CI | 约 1 天 | 违规无法合并，不依赖自觉 |
| 启动断言 + 架构守卫 | 约 1 天 | 根治"测试连生产库"这类历史顽疾 |
| **合计** | **约 4-5 天** | 换取全周期"文档即代码"的强制力 |

对比 bysj 的代价：因为缺这些，24 万行代码的工程化被判定为"薄弱"，返工成本远超 5 天。

## 8. 三条铁律（贴在 repo README 顶部）

> **1. 每写一个约束性文档章节（§2.2 数据权限 / §7 库存防线 / §9.2 Milvus 陷阱），旁边立刻配一个会失败的测试。**
>
> **2. 文档管「为什么」，测试管「必须」。凡是能用代码检查的，绝不用文档要求。**
>
> **3. 任何"约定"若无对应测试或 CI 检查，视为不存在。**

## 附录 B：不做什么（避免过度工程）

对应 PRD §14「明确不做」的精神，本方案也不引入：

- ❌ 不引入 SonarQube / 自建 CI 平台（GitHub Actions 足够）
- ❌ 不要求 100% 测试覆盖率（毕设不现实）；只要求 `tests/contract/` 与 `tests/invariants/` 全绿
- ❌ 不引入 K8s / 服务网格 / 复杂流水线
- ❌ 不引入 mypy strict（标准档用 pyright basic 即可）
- ❌ 不追求"AI 必须读文档"——已证明无效，改为"AI 必须过测试"
