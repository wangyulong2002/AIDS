## 1. 项目概述

### 1.1 项目背景
构建一个面向 C 端消费者的电商平台，覆盖「浏览—搜索—下单—支付—履约—售后」完整交易链路，并内置基于 RAG 的 AI 智能客服，降低人工客服成本、提升售前转化率与售后响应效率。

项目目标不是"能跑通"，而是**在单机可部署的前提下，完整体现商用电商的工程约束**：幂等、防超卖、最终一致性、数据权限、可观测性、降级容灾。

### 1.2 项目目标

| 维度 | 目标 |
|------|------|
| 交易能力 | 日均订单 **1 万单**，峰值下单 **10 TPS** |
| 读能力 | 峰值读 **500 QPS**（首页/详情/搜索） |
| AI 客服 | 解决率 ≥ 65%，7×24 响应，首字延迟 ≤ 2s |
| 可用性 | 核心交易链路 ≥ 99.95%，支付/订单数据零丢失 |
| 工程质量 | 下单链路无超卖、无重复扣款；支付回调 100% 幂等 |
| 交付形态 | 单机 Docker Compose 一键部署，全链路可演示 |

**容量换算依据**（用于消除指标间的量级矛盾）：

```
日均订单 1 万单，交易集中在 10 小时有效窗口
  均值 TPS = 10,000 / 36,000s ≈ 0.28 TPS
  峰值系数取 20  →  峰值下单 ≈ 6 TPS
  设计目标取 10 TPS（含约 1.7 倍余量）
读 QPS 500，读写比约 50:1，与浏览型电商流量特征吻合
```

> 上述为**设计目标**。压测在单机环境执行，且**压测目标高于设计目标**以证明架构余量：
> 下单链路压测至 **50 TPS**（设计目标的 5 倍）、读链路压测至 **1000 QPS**（设计目标的 2 倍），
> 达标即证明架构对设计目标有充分余量，压测报告需同时给出设计目标下的资源水位。
> **不引入分库分表**——10 TPS 下单（甚至 50 TPS 压测）单库完全可承载。仅在订单表设计上预留分片键（`user_id`），并在文档中标注拆分边界。

### 1.3 名词定义

| 名词 | 定义 |
|------|------|
| SKU | 最小库存单位 |
| SPU | 标准产品单位，多 SKU 聚合 |
| RAG | 检索增强生成（Retrieval-Augmented Generation） |
| Ark | 火山引擎方舟大模型服务平台，本项目的 LLM 统一接入层 |
| 人工兜底 | AI 无法解决时转人工客服的机制 |
| 幂等 | 同一请求重复执行结果一致，不产生副作用叠加 |
| IDOR | 越权访问（Insecure Direct Object Reference），电商最高频安全漏洞 |
| Mock 支付网关 | 自建的模拟支付渠道服务，保留真实签名/回调/对账形态 |
| 预扣 | 下单时先在 Redis 扣减可售库存，支付成功后再落 DB |

## 2. 用户角色与权限模型

### 2.1 角色

| 角色 | 说明 | 核心诉求 |
|------|------|----------|
| 游客 | 未登录用户 | 浏览商品、搜索 |
| 消费者 | 注册登录的买家 | 购买、支付、售后、咨询 |
| 商家/运营 | 后台管理人员 | 商品管理、订单履约、营销配置 |
| 客服人员 | 人工客服坐席 | 接管 AI 会话、处理工单 |
| 系统管理员 | 超级管理员 | 权限、审计、系统配置 |

### 2.2 权限模型（功能权限 + 数据权限，两者缺一不可）

**功能权限（RBAC）**：用户-角色-权限三层，菜单级 + 按钮级控制，所有后台写操作落审计日志。

**数据权限（行级）**：RBAC 只回答"能不能访问这个接口"，不回答"能不能访问这条数据"。**这是电商系统最高频的漏洞来源**，必须独立设计：

| 角色 | 数据范围规则 |
|------|-------------|
| 消费者 | 仅本人数据。订单、地址、优惠券、会话、评价的查询与操作，**服务端强制以 JWT 中的 userId 作为过滤条件**，禁止信任前端传入的 userId |
| 客服人员 | 仅本人接待的会话与其关联用户的可脱敏信息 |
| 商家/运营 | 全量商品与订单（本期单商家，不做商家维度隔离） |
| 系统管理员 | 全量 + 审计日志 |

> **关于 `sys_role.data_scope = 2`（本部门）**：本期为**单商家、无部门模型**，实际只会用到 `1`（仅本人）与 `3`（全量）。
> `2` 是给二期组织维度预留的取值，**本期不删除该枚举以免改动 DDL 与已核实的 38 表口径**，但必须定义退化行为：
> 若某角色被配成 `2`，数据权限过滤器按「全量 + 该角色权限点」处理，并在服务启动时打 **WARN 日志**提示该值本期未生效——
> 避免出现「配了 2 却静默查不到数据」这类无信号故障。BE-30 落地 RBAC 时按此实现。

**实现约定**：
- 统一从 JWT 解析当前用户身份，**业务代码不允许从请求参数读取 userId 用于权限判断**
- 资源访问必须做归属校验：`SELECT ... WHERE id = ? AND user_id = ?`，查不到即返回 403，而非 404（避免探测）
- 通过 SQLAlchemy 统一查询过滤器（Repository 基类强制注入 `user_id` 条件）实现数据权限，避免依赖开发者自觉
- 验收必测项：横向越权（用 A 的 Token 访问 B 的订单/地址/会话，必须全部 403）

**AI 客服技术约定**
- LLM 统一经火山引擎 **Ark API** 调用，模型可配置（后台可切换 endpoint/model），API Key 走服务端环境变量，**禁止前端暴露**
- 向量库：**Milvus**（standalone 起步，collection 按知识域划分：`product` / `policy` / `faq`）
- Embedding：经 Ark API 获取（如 doubao-embedding），维度与 Milvus collection schema 一致
- FastAPI 服务无状态，水平扩展；会话状态存 Redis
- **降级策略**（三级）：
  1. Ark API 超时/限流 → 重试（指数退避，最多 2 次）
  2. 仍失败 → 返回 FAQ 检索原文 + "当前智能客服繁忙"提示
  3. 检索也失败 → 直接引导转人工
- **AI 服务不可用不得阻塞交易链路**：AI 服务独立部署、独立线程池/连接池，与主业务服务无强依赖

## 4. 非功能需求

### 4.1 性能

| 指标 | 目标 |
|------|------|
| 核心接口（首页/详情/下单） | P99 ≤ 300ms |
| AI 客服首字延迟 | ≤ 2s（P95），整段流式输出 |
| 商品搜索 | P99 ≤ 500ms |
| 峰值读 QPS | 500（首页/详情走缓存，搜索走 MySQL 全文索引） |
| 峰值下单 TPS | 10 |
| 单机压测目标（高于设计目标，验证余量） | 下单 ≥ 50 TPS 无超卖；读 ≥ 1000 QPS |

> 设计目标为业务预估量级（日均 1 万单），压测目标刻意高于设计目标，用于证明架构余量与抗突发能力。压测报告需同时给出：① 压测峰值下的资源水位；② 设计目标（10 TPS / 500 QPS）下的资源水位。

### 4.2 可用性与可靠性
- 核心链路可用性 ≥ 99.95%；**AI 客服降级不影响交易链路**
- Kafka 生产端 `acks=all` + `enable.idempotence=true`，消费端幂等处理
- 订单/支付数据强一致；跨服务场景用**本地消息表 + 定时补偿任务**
- 所有涉及状态变更的异步操作必须**可重放且幂等**
- 关键写操作（下单/支付/退款）必须有对账或补偿机制兜底

### 4.3 安全
- 全站 HTTPS；接口 JWT 鉴权；后台操作审计
- **数据权限（横向越权防护）见 §2.2，为 P0 必测项**
- 支付回调验签、金额以服务端为准、幂等处理；Mock 网关同样执行完整验签流程
- SQL 注入 / XSS / CSRF 防护；上传文件做**类型白名单 + 大小限制 + 内容嗅探**，文件名重命名存储
- 敏感数据（手机号、身份证）脱敏存储与展示；密码 BCrypt（cost ≥ 10）
- 接口限流（Nginx + Redis 令牌桶）：登录/验证码/下单/支付接口单独限流
- AI 输出内容合规过滤

### 4.4 可运维性
- 结构化日志（JSON）+ `traceId` 全链路追踪，traceId 从 Nginx 贯穿到全部后端服务
- Prometheus + Grafana 监控告警：Python 运行时（uvicorn worker 存活、事件循环延迟、内存 RSS）、接口 RT、Kafka 堆积、Redis 命中率、Ark API 成功率、库存对账差异
- 配置管理：静态配置走 **pydantic-settings**（`.env` 本地覆盖）；动态配置（AI 阈值、坐席接待上限等）落 **`sys_config` 表**，后台可视化调整，经 Redis 发布订阅热更新，无需重启；单机 Compose 静态编排，无需服务注册中心
- 健康检查：所有服务暴露 `/health`，Docker Compose 配置 `healthcheck` 与依赖顺序

### 5.3 服务间通信约定

- 前端 → 主业务服务：REST，JSON，JWT（`Authorization: Bearer`）
- 前端 → AI 客服：Nginx 反代 `/api/ai/**` → AI 服务，SSE 流式
- 主业务服务 → AI 服务：内网 HTTP（知识库变更通知）
- AI 服务 → 主业务服务：内网 HTTP（订单工具查询，走内部接口）
- 异步事件：Kafka topic 清单见 §5.5

**JWT 跨服务鉴权（SSE 链路的真实难点）**

| 项 | 方案 |
|------|------|
| 签名算法 | **RS256**（PyJWT + cryptography）：主业务服务持私钥签发，AI 服务持公钥本地验签（避免 HS256 共享密钥在多服务间扩散） |
| 公钥分发 | 主业务服务暴露 `/.well-known/jwks.json`，AI 服务启动时拉取并缓存 |
| 前端 SSE 传参 | **`EventSource` 不支持自定义 Header**，故采用：优先 `fetch` + `ReadableStream` 手动解析 SSE（可带 Header）；降级方案为 URL query 传短期一次性 ticket（Redis 存 60s，用后即焚），**禁止直接 URL 传 Access Token** |
| 内部接口鉴权 | 内网网段限制 + 服务间静态 Token（环境变量下发）+ 请求签名（timestamp + nonce 防重放） |

### 5.6 商品搜索方案（MySQL 8 全文索引）

**决策（v1.2）**：**不引入 Elasticsearch**。商品搜索由 MySQL 8 内置全文索引承载，搜索数据与商品数据同库同事务。

```
商品写操作（增/改/删/上下架）
   → 直接写 biz_spu（单库单事务）
   → FULLTEXT 索引由 InnoDB 自动维护，无需同步
```

**为什么不引入 ES**：

| 维度 | 说明 |
|------|------|
| 数据规模 | 本平台商品量级 ≤ 10 万 SPU，单表全文索引完全可承载 |
| 性能要求 | 搜索 P99 ≤ 500ms、峰值 500 QPS，全文索引 + 组合索引即可满足 |
| 一致性 | 同库同事务 → **强一致**，免去同步链路、对账、补偿与死信治理 |
| 部署成本 | 少一个中间件（省约 1GB 内存与一份运维面），对单机毕设形态更友好 |

**实现要点**：

- 中文分词：`FULLTEXT INDEX ft_spu_name (name, subtitle) WITH PARSER ngram`（MySQL 内置 `ngram` 解析器，bigram 切分，**无需插件**）
- 检索：`MATCH(name, subtitle) AGAINST (? IN BOOLEAN MODE)`，与 `status = 2`（已上架）等条件组合
- 筛选：`category_id`（复用 `idx_category_status`）、`brand_id`、`min_price` 价格区间
- 排序：`sales DESC` / `min_price ASC|DESC` / `create_time DESC`（复用已有冗余字段）
- 分页：`LIMIT offset, size`，与统一分页规范一致
- 关键词高亮：服务端基于返回结果做简单匹配标注（不引入高亮组件）

**明确不做（本期）**：相关性调优（BM25/LTR）、同义词、拼写纠错、聚合分析、搜索日志分析。

> 若后续商品量级或检索要求显著提升，按 §15 决策路径再评估引入搜索引擎；届时搜索接口契约（`GET /product/search`）不变，仅替换实现。

## 6. 核心状态机与业务规则

> 本章为编码前必须冻结的内容。所有状态流转必须由服务端驱动，前端不得直接指定目标状态。

### 6.1 订单状态机

| 状态码 | 状态名 | 说明 |
|------|------|------|
| `PENDING_PAY` | 待付款 | 下单成功，等待支付 |
| `PAID` | 待发货 | 支付成功，等待商家发货 |
| `SHIPPED` | 待收货 | 已发货，等待用户签收 |
| `COMPLETED` | 已完成 | 已签收（可评价窗口内） |
| `AFTER_SALE` | 售后中 | 存在进行中的售后单 |
| `CANCELLED` | 已取消 | 未支付超时/用户主动取消 |
| `CLOSED` | 已关闭 | 已支付后取消（退款完成） |

**流转表**

| 起始 | 事件 | 目标 | 副作用 |
|------|------|------|--------|
| — | 提交订单 | `PENDING_PAY` | Redis 预扣库存、锁定优惠券、创建支付单 |
| `PENDING_PAY` | 支付成功回调 | `PAID` | DB 扣减锁定库存、核销优惠券、发 `order.paid` |
| `PENDING_PAY` | 15min 超时 / 用户取消 | `CANCELLED` | 回补库存、释放优惠券、关闭支付单 |
| `PAID` | 商家发货 | `SHIPPED` | 创建运单、发通知 |
| `PAID` | 用户申请取消 + 商家同意 | `CLOSED` | 全额退款、回补库存 |
| `SHIPPED` | 用户确认收货 / 15天自动 | `COMPLETED` | 发通知、开启评价窗口 |
| `COMPLETED` | 申请售后 | `AFTER_SALE` | 创建售后单 |
| `AFTER_SALE` | 售后单关闭 | `COMPLETED` / `CLOSED` | 依售后结果决定 |

- 终态：`CANCELLED`、`CLOSED`（评价完成后）
- 所有流转必须校验**当前状态合法性**（乐观锁 / 条件更新 `WHERE status = ?`），防并发覆盖

### 6.2 库存状态机

库存分三段记账，Redis 与 DB 双写：

```
Redis（可售 available）  ──下单预扣──▶  DB locked_stock +1
                                        Redis available -1

支付成功   → DB: locked -1, sold +1
超时/取消  → DB: locked -1, available +1（回补）
退款成功   → DB: sold -1, available +1（回补）
```

| 字段 | 含义 |
|------|------|
| `total_stock` | 总库存 |
| `available_stock` | 可售库存 |
| `locked_stock` | 已下单未支付锁定 |
| `sold_stock` | 已售出 |

约束：`total_stock = available_stock + locked_stock + sold_stock`（任意时刻恒等式，用于对账）

### 6.3 优惠券状态机

| 状态 | 说明 |
|------|------|
| `UNUSED` | 已领取未使用 |
| `LOCKED` | 下单锁定中（占用，不可再用） |
| `USED` | 已核销 |
| `EXPIRED` | 已过期 |
| `FROZEN` | 退款中冻结 |

流转：`UNUSED → LOCKED`（下单）→ `USED`（支付成功）/ `UNUSED`（超时取消回滚）
`UNUSED → EXPIRED`（定时任务扫描过期）

### 6.4 支付单状态机

| 状态 | 说明 |
|------|------|
| `INIT` | 已创建，待支付 |
| `PAYING` | 已发起支付，等待渠道回调 |
| `SUCCESS` | 支付成功 |
| `FAILED` | 支付失败 |
| `CLOSED` | 超时关闭 / 订单取消 |

- 终态：`SUCCESS`、`CLOSED`
- **回调幂等**：以 `out_trade_no`（商户订单号）为幂等键，`SUCCESS` 状态下重复回调直接返回成功，不重复触发业务

### 6.5 售后退款状态机

**仅退款**：`APPLIED` → `MERCHANT_REVIEW` → `REFUNDING` → `REFUND_SUCCESS` / `REFUND_FAILED`
**退货退款**：`APPLIED` → `MERCHANT_REVIEW` → `WAIT_RETURN` → `WAIT_RECEIVE` → `REFUNDING` → `REFUND_SUCCESS`

| 状态 | 说明 |
|------|------|
| `APPLIED` | 买家已申请 |
| `MERCHANT_REVIEW` | 商家审核中 |
| `REJECTED` | 商家拒绝（终态，买家可申诉/关闭） |
| `WAIT_RETURN` | 待买家寄回 |
| `WAIT_RECEIVE` | 待商家收货 |
| `REFUNDING` | 退款处理中 |
| `REFUND_SUCCESS` | 退款成功（终态） |
| `REFUND_FAILED` | 退款失败（需人工介入，告警） |
| `CANCELLED` | 买家撤销（终态） |

### 6.6 金额与优惠券规则

| 规则项 | 约定 |
|------|------|
| 金额精度 | 全部 `DECIMAL(12,2)`，禁止浮点 |
| 金额权威 | 订单金额**一律服务端重算**，前端传入金额仅用于比对，不一致则拒绝下单 |
| 券叠加 | 单订单最多使用 **1 张**优惠券 |
| 券门槛 | 按**商品实付金额**（不含运费）判断满减门槛 |
| 券互斥 | 本期不做叠加规则，二期扩展 |
| 退款分摊 | 优惠券金额按订单内各商品金额**比例分摊**；部分退款时按分摊后金额退，保证 `Σ退款 ≤ 实付` |
| 运费 | 运费模板：满 X 元包邮，否则固定运费 Y；偏远地区附加费 Z。运费**不参与优惠券分摊，全额退还** |
| 舍入 | 分摊金额采用"最后一件补差"法，避免累计误差 |

### 6.7 延迟任务方案（订单超时 / 自动收货）

> **Kafka 无原生任意延迟消息**，故不使用 Kafka 承担延迟语义。

**本期方案：Redis ZSet 时间轮**

```
投递：ZADD delay_queue <executeAt> <payload>
      payload = {bizType, bizNo, executeAt}

消费：定时任务（每秒）ZRANGEBYSCORE delay_queue 0 <now> LIMIT 0 100
      → 取出后 ZREM（Lua 保证原子，防多实例重复消费）
      → 执行关单 / 确认收货
      → 失败重试 3 次，仍失败写入死信表并告警
```

**补偿兜底**：每 5 分钟扫描一次"超时未关单"（`status = PENDING_PAY AND create_time < now - 16min`）与"超期未确认收货"的订单，做二次兜底。

> 该补偿任务是**资损防线**：关单失败会导致库存永久锁定，必须有兜底扫描。

### 6.8 幂等统一约定

| 场景 | 幂等键 | 实现 |
|------|--------|------|
| 提交订单 | 客户端生成 `submitToken` | Redis `SETNX submitToken 1 EX 300`，失败直接返回原订单 |
| 支付回调 | `out_trade_no` | 支付单状态机 + 条件更新 |
| 退款 | `refund_no` | 退款单状态机 + 唯一索引 |
| Kafka 消费 | `业务单号 + consumerGroup` | Redis 去重表（TTL 24h） |
| 延迟任务 | `bizType + bizNo` | ZREM 原子性 + 业务状态条件更新 |
| 库存回补 | `orderNo` | 条件更新 + `biz_stock_log` 唯一索引 |

**原则**：幂等判断必须基于**持久化状态**，不能只依赖 Redis（Redis 会丢数据）。

## 7. 库存与超卖控制

### 7.1 三层防线

| 层级 | 手段 | 作用 |
|------|------|------|
| 第一层 | **Redis Lua 脚本预扣** | 原子校验 + 扣减，挡住 99% 并发，避免请求打到 DB |
| 第二层 | **DB 乐观锁（version）** | 支付成功落库时 `UPDATE ... WHERE sku_id=? AND version=? AND available_stock >= ?`，失败重试 |
| 第三层 | **DB 约束兜底** | `available_stock >= 0` 检查约束 + 库存流水唯一索引，异常直接报错回滚并告警 |

### 7.2 关键设计点

- **预扣 Lua 脚本**（原子执行）：
  ```
  if redis.call('GET', stockKey) >= qty then
      redis.call('DECRBY', stockKey, qty)
      return 1
  else
      return 0
  end
  ```
- **Redis 库存预热**：服务启动 / 商品上架时从 DB 加载可售库存到 Redis；提供手动重载接口
- **热点行问题**：本期不做秒杀，普通商品 SKU 分散，单行竞争可控。若未来做秒杀，需引入库存分段（`sku_stock_segment`）打散热点
- **Redis 与 DB 不一致**：每 10 分钟定时对账，比对 Redis 可售数与 DB `available_stock`，差异超阈值告警 + 自动以 DB 为准重置 Redis
- **Redis 宕机**：预扣失败即下单失败（快速失败），不允许降级到直接扣 DB（会击穿）

### 7.3 验收要求

- 压测 50 TPS 并发抢购同一 SKU，**最终售出数量必须精确等于库存数**，无超卖、无少卖
- 库存恒等式 `total = available + locked + sold` 在压测前后均成立
- 杀进程测试：下单中途杀掉订单服务，恢复后库存对账无差异

## 8. 支付方案（Mock 支付网关）

### 8.1 为什么自建

个人主体无法申请支付宝/微信支付商户资质。但支付是电商系统的**资损核心**，必须完整实现，因此自建 Mock 网关**保留真实渠道的全部工程形态**：

| 保留的真实能力 | 说明 |
|------|------|
| 签名/验签 | RSA2（SHA256withRSA），商户私钥签名、渠道公钥验签 |
| 统一下单 | 商户订单号 `out_trade_no`、渠道订单号 `trade_no`、金额、异步通知地址 |
| 异步回调 | 支持配置**回调延迟、重复回调次数、回调丢失概率**（用于故障注入测试） |
| 主动查询 | 订单查询接口，用于回调丢失时的补偿 |
| 退款 | 全额/部分退款，退款单号 `refund_no`，退款回调 |
| 对账单 | T+1 生成对账文件（CSV），供商户对账任务拉取 |
| 沙箱支付页 | 提供模拟收银台页面（确认支付 / 取消支付 / 超时），供演示 |

### 8.2 支付主流程

```
1. 用户点击支付
   → 主业务调用 Mock 网关「统一下单」
   → 网关返回支付单号 + 沙箱支付页 URL
2. 用户在沙箱收银台操作（成功/失败/超时）
   → 网关异步回调主业务 /payment/callback
3. 主业务回调处理（必须幂等）：
   验签 → 校验金额与订单号 → 校验支付单状态
   → 条件更新订单 PENDING_PAY → PAID
   → 扣减 DB 锁定库存、核销优惠券
   → 发 Kafka order.paid
   → 返回 "success"（网关据此停止重推）
4. 若回调丢失 → 定时任务主动查询（每 1min 扫描 PAYING 超 5min 的支付单）
```

### 8.3 故障注入测试用例（验收必测）

| 用例 | 预期 |
|------|------|
| 回调重复推送 3 次 | 订单只流转一次，库存只扣一次 |
| 回调金额被篡改 | 验签通过但金额校验失败，拒绝处理并告警 |
| 回调签名错误 | 直接拒绝，记录审计日志 |
| 回调完全丢失 | 主动查询补偿任务在 5min 内完成状态修正 |
| 支付成功后杀进程 | 重启后状态一致，无重复发货 |
| 对账单存在差异 | 对账任务生成差异记录并告警 |

### 8.4 未来切换真实渠道

网关以 `PaymentChannel` 接口抽象（Python Protocol），Mock 实现与真实支付宝/微信实现遵循同一接口，切换只需更换适配器实现与配置，业务代码零改动。

## 9. AI 智能客服详细设计

### 9.1 处理流程

```
用户提问
   │
   ▼
[输入敏感词过滤] ──命中──▶ 拒答提示（记录审计）
   │
   ▼
[意图识别] (Ark API, 低温度, few-shot, 五分类)
   ├─ 订单查询 ──▶ 工具调用：查真实订单（见 §9.3）──▶ 生成回答
   ├─ 售前咨询 ──▶ Milvus 检索 product 域 Top5
   ├─ 售后/政策 ─▶ Milvus 检索 policy 域 Top5
   ├─ 转人工   ──▶ 直接触发 handoff
   └─ 闲聊/其他 ─▶ 通用 Prompt + 检索 faq 域
   │
   ▼
[拼装 Prompt] system 人设 + 检索上下文(带引用) + 最近10轮历史
   │
   ▼
[Ark API 流式生成] ──▶ SSE 推送前端
   │
   ▼
[输出过滤] + 落库 + 满意度埋点
   │
   ▼
[置信度评估] ──低置信/争议/不满──▶ 转人工
```

### 9.2 RAG 知识库设计

| 项 | 约定 |
|------|------|
| 知识源 | 商品详情（自动同步）、售后政策、FAQ、物流说明 |
| 切片 | 500 token / 片，50 token overlap，按语义边界（标题/段落）切分优先 |
| 元数据 | 每片携带 `source_type`、`source_id`、`title`、`version`、`updated_at` |
| 检索 | Milvus 相似度检索 Top5；可选**混合检索**（向量 + BM25 关键词）提升召回 |
| 检索前置 | 集合必须**显式 load** 后才能向量检索：未 load 时 `search` **静默返回空数组且不报错**（`insert`/标量 `query` 不受影响）。AI-05 服务启动与 AI-06 重建流程都必须在切别名前完成 load |
| 重排 | 二期引入 Rerank 模型；本期按相似度阈值过滤 |
| 引用 | 回答中标注知识来源（前端可展开原文），降低幻觉感知 |
| 重建 | 知识库变更 → Kafka `kb.index.rebuild` → FastAPI 异步重建对应域索引（先建新 collection 再切别名，避免检索中断） |

> **v1.3 实机确认**：重建流程「先建新 collection 再切别名」存在一个隐蔽陷阱——新集合若未 `load` 就切别名，
> 切换瞬间检索会从「有结果」变成**静默的空结果**（HTTP 200、不抛异常），恰好制造该设计本想避免的检索空窗。
> 故重建脚本的固定顺序为：建集合 → 灌数据 → **load** → 探活（用已知向量 `search` 断言命中）→ 再切别名。

### 9.3 订单查询工具调用（Function Calling）

- AI 服务通过**内部接口**调用主业务服务查询订单，需携带 `userId`（从用户 JWT 解析），**只能查当前用户自己的订单**
- 支持查询：订单列表、订单详情、物流轨迹、退款进度
- 结果以结构化 JSON 注入 Prompt，要求 LLM **仅转述不臆造**
- 工具调用结果需脱敏（手机号、详细地址）

### 9.4 置信度与转人工触发

> **生成式模型没有原生置信度**，必须显式构造。本项目采用**多信号融合**：

| 信号 | 来源 | 低置信判定 |
|------|------|-----------|
| S1 检索相似度 | Milvus 返回的 distance/score | Top1 相似度 < 阈值（可配置，默认 0.65） |
| S2 上下文支撑度 | 二次 LLM 判定（低温度，"回答是否完全由给定上下文支持" yes/no） | 判定为 no |
| S3 意图置信度 | 意图识别模型输出 | 五分类置信度 < 阈值 |
| S4 规则信号 | 业务规则 | 涉及金额争议、投诉、法律、连续 2 轮负面情绪 |

**转人工触发条件（任一命中）**：
1. 用户显式要求（"转人工"/"人工客服"）
2. S1 / S2 / S3 任一低置信
3. S4 规则命中
4. 同一问题连续 3 轮未解决
5. 用户连续两次表达不满（情绪识别）

阈值全部落 `sys_config` 动态配置表，后台可视化调整，经 Redis 发布订阅热更新，变更无需重启。

### 9.5 转人工工作台

**坐席管理**

| 项 | 约定 |
|------|------|
| 坐席状态 | `ONLINE` / `BUSY` / `OFFLINE`（Redis 存储，心跳 30s 续期） |
| 接待上限 | 每坐席默认 5 个并发会话（`sys_config` 可配置） |
| 分配策略 | 优先"在线且未达上限"中当前会话数最少者；无可用坐席则入排队队列 |
| 排队 | Redis List 队列，超 60s 无坐席接入则提示用户留言 |
| 会话转移 | 支持坐席转交、管理员强制指派 |

**客服端功能**
- 会话列表（待接入 / 进行中 / 已结束），未读标记
- 用户画像侧栏：基础信息、最近订单快照、历史会话
- 消息收发、快捷回复模板、知识库检索（可一键发送检索结果）
- 接管 / 结束会话、标记解决状态

**AI 静默旁听**
- 转接后 AI 继续接收消息，异步生成**建议回复（draft）**，仅客服可见
- 客服可一键采用、编辑后发送或忽略
- 旁听内容不计入用户可见会话，避免 AI 与人工同时回复造成混乱
- 全部记录落 `ai_handoff_record`，用于后续优化

### 9.6 解决率定义（可度量）

> 1.2 节的"解决率 ≥ 65%"必须有操作化定义，否则不可验收。

**会话解决** = 同时满足：
1. 未转人工，或转人工后由客服标记为"已解决"
2. 会话结束后 **30 分钟内**用户未就同类意图再次发起咨询
3. 该会话满意度反馈不为 👎（无反馈视为中性，计入分母）

```
解决率 = 判定为「已解决」的会话数 / 总有效会话数
总有效会话数 = 用户消息数 ≥ 2 的会话（过滤掉误触、测试会话）
```

### 9.7 评测方案（M5 前置）

| 项 | 约定 |
|------|------|
| 评测集 | **150 题**：售前 50 / 订单 50 / 售后 50，含标准答案与得分要点 |
| 标注 | 项目组人工标注，冻结为基线，不得随模型调整而修改 |
| 判定 | LLM-as-judge 初判 + 人工抽检 20% 复核 |
| 指标 | 正确率、幻觉率（编造信息占比）、转人工准确率（该转的转了 / 不该转的没转） |
| 回归 | 每次知识库变更或 Prompt 调整后跑一次，指标下降超 5% 阻断发布 |

### 9.8 会话状态机

`AI_SERVING` → `HANDOFF_REQUESTED` → `HUMAN_SERVING` → `CLOSED`

支持 `HUMAN_SERVING → AI_SERVING`（客服转回 AI）、`CLOSED → AI_SERVING`（用户重新发起）。

**成本估算（Ark API）**

```
假设：日均 1000 次客服会话，平均 6 轮，每轮 input 3000 token / output 300 token
  input:  1000 × 6 × 3000 = 18M token/日
  output: 1000 × 6 ×  300 = 1.8M token/日
按 doubao 系列定价估算，日成本在数元至数十元量级
→ 开发/演示阶段建议：设置日预算上限 + 缓存高频问答 + 评测集离线跑
```

**上界推导（用于设预算告警阈值，DEP-11 前须用火山方舟定价页校准单价）**

| 情形 | input 单价（元/百万 token） | output 单价（元/百万 token） | 日成本 | 月成本(30 日) |
|------|---------------------------|-----------------------------|--------|---------------|
| 下界 | 0.6 | 4 | 18 元 | ≈ 540 元 |
| **上界（取高值）** | **1.2** | **8** | **36 元** | **≈ 1080 元** |
| 上界 × 峰值日（大促 3 倍会话量） | 1.2 | 8 | **108 元** | — |

> 表内单价是**为推导上界而设的假设区间**，非实时报价，接入前必须核实并回填；真正的护栏是下面这条：
> **在 Ark 侧设硬阈值告警：日成本 > 80 元告警、> 150 元自动降级**（只保留检索式回答、关闭多轮改写），
> 使最坏情况有上界可兜。三项已落地的降本手段（高频问答缓存、评测集离线跑、Top5 上下文裁剪）可使实际值显著低于上界。

## 12. 验收标准

> 每条均给出可执行判定方式，不接受"人工感觉良好"式验收。

### 12.1 功能验收
- [ ] 全部 P0 需求实现，通过前后端联调；提供完整功能演示脚本（含异常路径）
- [ ] 订单状态机、库存状态机、支付状态机、售后状态机全部流转正确，非法流转被拒绝

### 12.2 交易正确性（核心）
- [ ] **无超卖**：50 TPS 并发抢购同一 SKU，售出数量 == 库存数，误差为 0
- [ ] **无重复扣款**：同一 `submitToken` 并发提交 100 次，仅生成 1 笔订单
- [ ] **库存恒等式**：压测前后 `total = available + locked + sold` 均成立
- [ ] **金额一致**：篡改前端提交金额，服务端拒绝并告警

### 12.3 支付与幂等
- [ ] 回调重放 3 次，订单只流转一次、库存只扣一次
- [ ] 签名错误 / 金额篡改的回调被拒绝并记审计日志
- [ ] 回调丢失场景下，主动查询补偿在 5 分钟内修正状态
- [ ] 支付成功瞬间杀进程，重启后状态一致、无重复发货
- [ ] T+1 对账任务能识别人为构造的差异并告警

### 12.4 数据权限（安全）
- [ ] 用 A 的 Token 访问 B 的订单 / 地址 / 优惠券 / 会话，全部返回 403
- [ ] 遍历式 IDOR 扫描（批量请求递增 ID）无一条越权数据泄露

### 12.5 AI 客服
- [ ] 150 题评测集正确率 ≥ 85%，幻觉率 ≤ 5%（附评测报告）
- [ ] 首字延迟 P95 ≤ 2s，流式输出无卡顿
- [ ] 转人工：4 类触发条件逐条验证可触发，工作台可接管、可结束、可标记解决
- [ ] AI 静默旁听生成建议回复，客服可一键采用
- [ ] 知识库变更后索引重建成功，重建期间检索不中断

### 12.6 容灾与降级
- [ ] **Ark API 故障注入**（关闭 Mock Ark 或断网）：客服降级为 FAQ 原文 + 转人工引导，**交易链路完全不受影响**
- [ ] **Redis 宕机**：下单快速失败并给出明确提示，无脏数据
- [ ] **Kafka 停机**：生产端本地消息表堆积，恢复后自动补发，无消息丢失
- [ ] Kafka 消费端杀进程重启，消息不丢不重（幂等验证）

### 12.7 工程质量
- [ ] 全链路 `traceId` 可追踪（从 Nginx 贯通全部后端服务日志）
- [ ] Prometheus 监控覆盖核心链路，告警规则可触发
- [ ] 安全扫描无高危漏洞；敏感数据脱敏检查通过
- [ ] 单机 Docker Compose 一条命令拉起全栈并健康检查通过

| 支付对账差异 | 高 | T+1 自动对账 + 差异告警 + 人工处理流程（§8.3） |
| 横向越权（IDOR） | 高 | 数据权限模型 + 统一拦截器 + 专项渗透测试（§2.2、§12.4） |
| 异步消息丢失/重复 | 中 | 本地消息表 + 消费幂等 + 死信队列 + 杀进程重放测试 |
| RAG 幻觉误导用户 | 中 | Prompt 约束「仅依据知识库回答」+ 引用溯源 + 上下文支撑度判定（S2）+ 免责话术 |
| Milvus 运维复杂度 | 中 | standalone + Docker Compose；数据量 > 千万级再上集群 |
| 单机资源不足（多中间件同机） | 中 | 最低配置建议（宿主可用内存下限）：最小档 ≥2GB / 默认档 ≥3.5GB / 全量档 ≥6GB，8GB 为舒适值——**口径与 `deploy/README.md`、`deploy/docker-compose.yml` 一致，以本机实测为准**；v1.2 移除 ES、v1.3 移除 Nacos 后占用持续下降；压测按单机上限缩比，报告说明差异 |
| 置信度阈值调参困难 | 中 | 阈值配置化 + 评测集回归 + 可视化调参（§9.4、§9.7） |
| AI 输出违规内容 | 中 | 输入输出双向过滤 + 日志留痕审计 + 可选内容安全 API |
| 毕设周期超期 | 中 | M0 冻结需求；P2 需求一律砍掉；M5 可独立降级为"仅 FAQ 检索"保底 |
