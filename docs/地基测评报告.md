**这是一份设计规格少见地高的地基**——它真的把「文档里的约定」翻译成了「会失败的测试」，而不是停在口号（33 项文档一致性门禁可实跑通过、扫描器有违规样本回归、护栏有自检）。

## 2. 先说做得对的（真实踩过坑才有的实现）

### 2.1 文档一致性门禁是真闸门，不是装饰

实跑 `python docs/tools/gen_data_dictionary.py --check -v` → **PASS 33 项全部一致**。

它有两点超出常见水准：

- **双向防漂移**：不仅校验「DDL 表数 == VERSIONS 期望」，还反向校验「VERSIONS 声明值 == 脚本期望值」。两侧任一侧改错都会红，不存在「改文档蒙混过关」。
- **纯标准库实现**（只用 argparse/re/pathlib），因此**不会因为依赖装不上而被跳过**——这正是它敢当 CI 第一步的前提（`.github/workflows/ci.yml:39-53`）。

### 2.2 契约测试真的在解析文档，没有抄一遍

`tests/contract/_doc_parser.py` 逐行读 `docs/DATA-DICTIONARY.md` 的 markdown 表格与 `docs/sql/schema.sql` 的 DDL 正则抽取（`_doc_parser.py:264-267, 333-335`）。

README §核心设计声称「不抄文档内容」——**经核对属实**。抄写本身就是新的漂移点，作者绕开了它。

### 2.3 扫描器有「自己会不会漏检」的回归测试

`tests/contract/test_error_codes.py:106-134` 定义 6 种规避写法 + 3 种合法写法，双向断言：

```python
_EVASIONS = ['fail(10001, "...")', '{"code": 40002}', "raise BizError(50001)",
             "error_code = 70001", '{"code": 90001}', "{**base, 'error_code': 30003}"]
```

我实测 `scan_file()`：`{"code": 40002}` 与 `err_code = 50001` 均被正确报出，`order.status == 20` 也被 C2 报出。**扫描器有牙**。

### 2.4 护栏自检测试——防「护栏误伤」，这是被忽略最深的失效模式

`tests/invariants/test_guard_selfcheck.py` 断言四件事，其中最有价值的是：

> `git check-ignore --no-index` 之所以必须加 `--no-index`：默认不报告已跟踪文件，所以当 `*/_*.py` 把 `app/__init__.py` 挡在版本库外时，`check-ignore` 看起来一切正常——这正是那个 bug 能长期潜伏的原因。（`test_guard_selfcheck.py:17-20`）

这段注释本身就是高质量的工程遗产。

### 2.5 启动断言继承 `SystemExit`，防被 `except Exception` 吞掉

`app/core/config.py:43-52` 让 `StartupAssertionError` 继承 `SystemExit`，并有专门测试验证：

```python
def test_not_caught_by_except_exception(self):
    ...  # test_startup_assertions.py:147-157
```

配置错误在进程启动阶段终止，不降级为「一个业务异常」。这是一个想清楚了才写得出的细节。

### 2.6 其余亮点（简列）

- **扫描器豁免按相对路径而非文件名**（`scan_error_codes.py:38-41`）——修正了「任何 `app/**/errors.py` 都自动免疫」的旧坑。
- **`.gitignore` 刻意不用 `_*` 宽泛规则**（`.gitignore:63-70`），并写明历史教训与替代方案。
- **C2 不再豁免 `0/1`**（`scan_enum_magic_numbers.py:27-30`）——因为 11 组枚举中有 10 组含 0/1 成员。
- **Dockerfile 安全基线**：多阶段构建、只复制已编译依赖不带工具链、非 root、`server_tokens off`。
- **HTTP 状态码语义清晰**：业务失败 200 + 5 个例外，且例外表**单一定义**（`app/core/response.py:95-101`），`exceptions.py` 只查询不复制。

## 4. P0 阻断级

### P0-1 基线不绿：护栏自检测试必然失败

**现象**：`tests/contract/_targets.py` 已入库，但 `scripts/hooks/forbid_temp_files.sh` 的白名单没有它，导致该文件被判定为「临时残留文件」。

**证据**：

```
$ git ls-files tests/contract/
tests/contract/_targets.py          ← 已受跟踪

$ bash scripts/hooks/forbid_temp_files.sh tests/contract/_targets.py
禁止提交临时/残留文件: tests/contract/_targets.py
HOOK_EXIT=1

$ bash scripts/hooks/forbid_temp_files.sh $(git ls-files)
HOOK_ON_ALL_TRACKED_EXIT=1          ← 唯一命中项就是 _targets.py
```

白名单只有两项（`scripts/hooks/forbid_temp_files.sh:21-26`）：

```bash
_is_whitelisted() {
  local path="$1" base="$2"
  [ "$base" = "__init__.py" ] && return 0
  [ "$path" = "tests/contract/_doc_parser.py" ] && return 0
  return 1
}
```

**影响**：
1. `test_guard_selfcheck.py:87-93` 的 `test_does_not_block_any_tracked_file` 断言 `== 0`，**必然失败**；CI 的 `pytest tests/invariants -q -m invariant`（`ci.yml:192`）会跑到它 → **invariants job 必红**。基线声称全绿，实际不绿。
2. 该文件此后**任何修改都无法通过 pre-commit**，只能 `--no-verify` 绕过——而「一旦养成绕过的习惯，整套门禁就都废了」正是项目文档反复警告的反模式（`test_guard_selfcheck.py:8-9`）。

**锐评**：这个自检测试存在的**唯一目的**就是防这类误伤，结果新加的 `_targets.py` 又踩了同一个坑，而自检测试还真把它抓住了——**护栏设计是对的，但没人跑过它**。

**修复**（一行）：

```bash
# scripts/hooks/forbid_temp_files.sh
[ "$path" = "tests/contract/_targets.py" ] && return 0
```

### P0-2 `_targets.py` 是死代码，扫描门禁漏掉整个服务层

**现象**：为「把新增服务包纳入扫描面」而专门抽出的 `_targets.py::scan_targets()`，**零调用点**。

**证据**：

```
$ grep -rn "scan_targets" --include=*.py .
tests/contract/_targets.py:22:def scan_targets() -> list[Path]:     ← 仅定义，无调用
```

两个扫描器的默认目标仍是旧的硬编码：

```
C4 _default_targets  : ['F:/AIDS/app']
C2 _default_targets  : ['F:/AIDS/app']
_targets.scan_targets: ['F:/AIDS/app', 'F:/AIDS/aids-backend/aids_backend']   ← 正确但没人用
```

CI 与 pre-commit 亦显式传 `app`（`ci.yml:80,83`；`.pre-commit-config.yaml:65,72` 的 `^app/.*\.py$`）。

**影响**：`aids-backend/aids_backend/` 下 **11 个业务文件**（`handlers.py` 5.8KB、`api/{user,product,order,pay,marketing,admin,health}.py`、`main.py`、`app_factory.py`）**完全不受 C2/C4 门禁保护**，同时也不在 `ruff format --check app tests`（`ci.yml:74`）与 `pyright include = ["app","tests"]`（`pyproject.toml:102`）的范围内。

这是教科书式的**静默缺口**：门禁全绿，但一半代码从未被检查过。

**自相矛盾之处**：`_targets.py:8-9` 的 docstring 自述

> 历史坑：本函数（原分别写在两个扫描器里）长期只返回 `PROJECT_ROOT / "app"`，BE-01 新增的 `aids-backend/aids_backend/` 因此**完全不在扫描范围内**。

——**修复被写出来了，但没有接线**。比修复前更危险，因为它看起来像已经修好了。

**附加风险（接线后会立刻撞上）**：实跑 C2 扫 `aids-backend` 时立即产生误报：

```
aids-backend\aids_backend\handlers.py:69: 状态字段 `status` 与魔法数字 500 比较
aids-backend\aids_backend\handlers.py:73: 状态字段 `status` 与魔法数字 400 比较
```

这两行是 `if status >= 500:` / `elif status >= 400:` —— **HTTP 状态码**，不是业务状态枚举。大概率这正是「接线后 CI 变红，于是搁置」的原因。

**修复方向**：
1. 两个扫描器的 `_default_targets()` 改为 `return scan_targets()`（并删掉各自的重复实现）；
2. CI / pre-commit 不再显式传 `app`（或改为传全部服务包）；
3. `handlers.py:69,73` 加行尾 `# enum-ok`（机制已支持，`scan_enum_magic_numbers.py:235-237`），或把 C2 的 `status` 判定收窄为「值落在已知枚举取值集合内才报」；
4. 新增契约测试：断言 `scan_targets()` 覆盖所有 `aids-*/aids_*` 目录——**这个缺口之所以逃逸，就是因为没有任何测试断言"扫描面"本身**。

### P0-3 三个服务 Dockerfile 的 `COPY` 源路径全部不存在

**现象**：三个 Dockerfile 都 `COPY <服务>/app`，但这些路径在文件系统上全都不存在。

**证据**：

```
deploy/app/backend.Dockerfile:48   COPY --chown=aids:aids aids-backend/app ./app
deploy/app/ai.Dockerfile:47        COPY --chown=aids:aids aids-ai/app ./app
deploy/app/mock.Dockerfile:51      COPY --chown=aids:aids aids-mock/app ./app

$ ls aids-backend/
aids_backend/      requirements.txt          ← 没有 app/
$ ls aids-ai/
requirements.txt                             ← 连服务代码都没有
$ ls aids-mock/
requirements.txt
$ ls aids-backend/app
ls: cannot access 'aids-backend/app': No such file or directory
```

且三者 CMD 均为 `gunicorn app.main:app`，而代码侧的真实包名是 `aids_backend`（`tests/api/test_route_contract.py:20` 即 `from aids_backend.api import MODULE_ROUTERS`）。

**四处产物互相矛盾**：

| 来源 | 声明的包名 |
|---|---|
| `deploy/app/*.Dockerfile` | `app` |
| 磁盘目录 | `aids_backend` |
| 测试 import | `aids_backend` |
| `_targets.py:19` `SERVICE_PACKAGE_GLOB = "aids-*/aids_*"` | `aids_backend` |

而 `_targets.py:18` 的注释还写着「与 `deploy/app/*.Dockerfile` 的 COPY 目标一致」——**实际并不一致**。

**对照 commit `f309978 "refactor: 服务包统一命名为 app，ORM/Docker/CI 契约层收敛"`**：声称统一命名为 `app`，但只改了 Dockerfile，代码包名/测试 import/扫描器 glob 三处都没跟上。**改名做了一半。**

**为什么能潜伏**：
- `deploy/docker-compose.yml` 的 9 个服务**全是中间件**（mysql/redis/nginx/kafka/minio/minio-init/milvus×3），**根本没有 backend/ai/mock**；
- CI smoke 只跑 `docker compose config`（`ci.yml:238-239`），**不 build**；
- 文档一致性门禁只校验「Dockerfile 文本里的 EXPOSE 端口集合 == {8000,8080,8081}」，**不校验 COPY 源在文件系统上是否存在**。

三道防线全部绕过了这个位置。

**影响**：T1 一旦执行 `docker build`，立即失败，且报错是「路径不存在」，与「命名收敛」的意图完全脱节，排查成本高。

**修复方向**：确定单一命名（建议 `aids-backend/app/`），一次性同步四处：磁盘目录 + 代码包名 + 测试 import + Dockerfile；并为 `aids-ai/`、`aids-mock/` 补齐服务目录骨架。
