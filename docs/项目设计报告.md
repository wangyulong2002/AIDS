## 0. 一句话结论

**AIDS 当前不是一个"电商系统"，而是一套"把电商设计文档钉死在代码上的工程护栏"。**

它 50 个受跟踪文件里有 3 类是主角：**3 份 SSOT 源码**（枚举 / 错误码 / 响应体）、**8 类契约测试 + 2 个扫描器**（把文档事实变成会失败的断言）、**三层门禁**（pre-commit → GitHub Actions → compose 冒烟）。业务代码是零——这是刻意的：先把"做什么必须对"钉好，再写实现。

它要根治的是同工作区 `bysj/` 的病：有 12 万字设计文档，工程化仍然薄弱。根因在 `docs/工程化门禁方案.md` §1 写得很直白——门禁装在**输入端**（读没读文档），而"读过"无法验证，必然沦为形式合规。所以 AIDS 把门禁全部搬到**输出端**：不问你读没读，只问你交的代码能不能过契约测试。

## 4. 关键机制设计（读代码前先懂这四条）

### 4.1 单一定义 + 反向校验（SSOT）

```
app/domain/enums.py          ← 唯一权威定义（IntEnum）
        ↕  tests/contract/test_enum_mapping.py 逐项比对
docs/DATA-DICTIONARY.md §一   ← 唯一权威映射表
```

同样结构复制到错误码（`errors.py` ↔ `API.md` §1.2/1.3）与统一响应（`response.py` ↔ `API.md` §1.1）。**两侧任何一侧漂移，CI 立刻变红——双向都拦得住**（既拦"文档改了代码没改"，也拦"代码登记了文档里没有的"）。

## 8. 这个仓库最值得学的三个设计

1. **把"约定"翻译成"退出码"**。`gen_data_dictionary.py` 把"表数必须是 38""服务数必须是 9""TASKS 必须是 97 项"（原为 96，见 §9.1）这些原本靠人工核对的数字变成了非零退出。文档里还留了**门禁能红的证据**：临时改字段类型、改表头数字，均立即 `exit=1`。
2. **护栏本身要被测试**。`test_startup_assertions.py` 的存在理由是：*护栏自己写错了会安静地不生效，这比没有护栏更危险*。所以每个断言都有正例与反例。
3. **每一步决策都留痕**。"为什么不用 ES""为什么不用物理外键""为什么禁用裸 SHA-256""为什么不把 `docs/sql` 直接挂载""为什么 MinIO 改用 quay.io"——每个"不选"都写清了触发原因。一个"没做什么、因为什么"的记录，比十页"我们做了什么"更有长期价值。

### 9.6 两份 `.env.example` 键名分叉（生产启动风险最高的一条）

`app/core/config.py` 的生产断言要求 `FIELD_ENCRYPT_KEY` / `FIELD_HMAC_KEY` / `ARK_API_KEY`，但**编排层的 `deploy/.env.example` 用的是另一套键名**：

| 语义 | 根 `.env.example`（进程层） | `deploy/.env.example`（编排层） |
|------|------------------------------|--------------------------------|
| 字段加密密钥 | `FIELD_ENCRYPT_KEY` | `MOBILE_AES_KEY` |
| 字段哈希密钥 | `FIELD_HMAC_KEY` | `MOBILE_HMAC_KEY` |
| JWT TTL | `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` | `JWT_ACCESS_EXPIRE_SECONDS` / `JWT_REFRESH_EXPIRE_SECONDS` |
| 内部服务鉴权 | `INTERNAL_SERVICE_TOKEN` / `INTERNAL_SIGN_SECRET` | `INTERNAL_TOKEN` / `INTERNAL_SIGN_KEY` |
| 模型名 | `ARK_MODEL` | `ARK_CHAT_MODEL` |
| MinIO 桶 | `MINIO_BUCKET`（单桶） | `MINIO_BUCKET_PRODUCT` 等 4 个 |
| `SECRET_KEY` | 有 | **无** |

两个文件服务不同层次（进程 vs compose），但**键名不统一会让"按 deploy/README 的 `cp .env.example .env` 起服务"这条路在 production 直接启动失败**。更值得注意的是：门禁脚本 `check_env_hygiene()` 只校验 `deploy/.env.example`（与 compose 的 `${VAR}` 引用是否齐全、有无重复键），**根 `.env.example` 完全不在门禁覆盖内**——这类漂移不会被任何检查抓到。

**修复（2026-09-23）**：已按「以根 `.env.example`（应用侧）为权威命名」统一，`deploy/.env.example` 的应用段全部改名对齐。

| 语义 | 统一后的键（原 `deploy` 侧旧名） |
|---|---|
| 数据源 | `DATABASE_URL`（原 `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`） |
| Redis | `REDIS_URL`（原 `REDIS_HOST`，不再复用 `REDIS_PORT`/`REDIS_PASSWORD`） |
| 字段加密 / 哈希 | `FIELD_ENCRYPT_KEY` / `FIELD_HMAC_KEY`（原 `MOBILE_AES_KEY` / `MOBILE_HMAC_KEY`） |
| JWT TTL | `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL`（原 `JWT_ACCESS_EXPIRE_SECONDS` / `…_REFRESH_…`） |
| 内部服务鉴权 | `INTERNAL_SERVICE_TOKEN` / `INTERNAL_SIGN_SECRET`（原 `INTERNAL_TOKEN` / `INTERNAL_SIGN_KEY`） |
| 模型名 | `ARK_MODEL`（原 `ARK_CHAT_MODEL`） |
| Mock 渠道 | `MOCK_PAY_BASE_URL` / `MOCK_PAY_MERCHANT_ID` / `MOCK_PAY_RSA_PRIVATE_KEY_PATH`（原 `MOCK_PAYMENT_*`） |
| 补齐到 `deploy` 侧 | `SECRET_KEY`、`APP_ENV`、`MILVUS_COLLECTION` —— 缺 `SECRET_KEY` 即触发 S1-b 拒绝启动 |
| 补齐到根文件 | `ARK_EMBEDDING_MODEL` / `ARK_EMBEDDING_DIM` / `ARK_DAILY_BUDGET_TOKENS` / `MOCK_CALLBACK_*`（原仅存于 `deploy` 侧） |

**一处刻意例外**：MinIO 桶保留 4 键（`MINIO_BUCKET_PRODUCT` 等），而非第一套的单桶 `MINIO_BUCKET` —— 因为 `docker-compose.yml` 的 `minio-init` **已经实际创建了这 4 个桶**，按单桶改会让配置与实现重新矛盾。前缀仍是第一套的 `MINIO_BUCKET`。

**防复发（本次同时补的门禁）**：`check_env_hygiene()` 新增 2 项断言 ——
① 根 `.env.example` 无重复定义的键；② **根 `.env.example` 的每个键都必须在 `deploy/.env.example` 中有同名定义**（`deploy` 允许持有编排专属的额外键）。
至此"根改名、编排层没跟上"这类漂移会在 CI 第一步被拦下。门禁项数因此由 **33 → 35**。

> 历史叙述（§1 第二轮快照、§11/§12 的核查记录）中的"33 项"记录的是**当时的运行结果**，按 §9.7 的惯例原样保留，未随本次变更改写。

### 12.8 这次修复暴露的五条一般规律

| 规律 | 本轮证据 |
|------|----------|
| **门禁的失效是静默的，唯一防线是"给门禁本身写回归用例"** | 扫描器规则一松（`0/1` 豁免、区间漏 `9xxxx`、白名单含 `→`）不会报错，只是抓不到。本轮为 C2/C4/IDOR 各补了一组回归用例——**它们是"门禁还在工作"的唯一证据** |
| **豁免必须按"路径 / 精确词"，不能按"文件名 / 纯标点"** | `{"errors.py"}` 让任何 `app/**/errors.py` 免疫；`"→"` 让任何带箭头的行整行豁免；`p.name != "security.py"` 同理；`forbid_temp_files.sh` 的 `_*` 让 `__init__.py` 被判成残留。四处都是同一个错的四种写法 |
| **护栏不只可能漏报，还会误伤——而误伤更快杀死门禁** | `_*` 类规则把 `__init__.py`、`_doc_parser.py` 判为违规 → 合法改动无法提交。开发者面对"门禁拦住了正确的事"只有两条路：改门禁，或 `--no-verify`——后者一旦成为习惯，整套门禁就废了。所以**误伤必须当天修掉，并留下常驻回归用例**（本轮的 `test_guard_selfcheck.py` 13 条） |
| **用私有规则维持的"干净"不是干净** | `.git/info/exclude` 藏了 16 个文件，其中 3 个是合法 workflow 名——换台机器 `git add -A` 就是一次"多了三条流水线"的事故 |
| **只在文档里写的验收标准等于没写** | DEP-05 把"CI 第一步 + pre-commit 钩子"写得很清楚，但两个都没落地。**这与 bysj 的病同源，只是发生在了"门禁项目"自己身上**——正好印证 README 铁律第 3 条：*任何"约定"若无对应测试或 CI 检查，视为不存在* |
