## 0. 一句话结论

**AIDS 当前不是一个"电商系统"，而是一套"把电商设计文档钉死在代码上的工程护栏"。**

它 46 个文件里有 3 类是主角：**3 份 SSOT 源码**（枚举 / 错误码 / 响应体）、**8 类契约测试 + 2 个扫描器**（把文档事实变成会失败的断言）、**三层门禁**（pre-commit → GitHub Actions → compose 冒烟）。业务代码是零——这是刻意的：先把"做什么必须对"钉好，再写实现。

它要根治的是同工作区 `bysj/` 的病：有 12 万字设计文档，工程化仍然薄弱。根因在 `docs/工程化门禁方案.md` §1 写得很直白——门禁装在**输入端**（读没读文档），而"读过"无法验证，必然沦为形式合规。所以 AIDS 把门禁全部搬到**输出端**：不问你读没读，只问你交的代码能不能过契约测试。

## 4. 关键机制设计（读代码前先懂这四条）

### 4.1 单一定义 + 反向校验（SSOT）

```
app/domain/enums.py          ← 唯一权威定义（IntEnum）
        ↕  tests/contract/test_enum_mapping.py 逐项比对
docs/DATA-DICTIONARY.md §一   ← 唯一权威映射表
```

同样结构复制到错误码（`errors.py` ↔ `API.md` §1.2/1.3）与统一响应（`response.py` ↔ `API.md` §1.1）。**两侧任何一侧漂移，CI 立刻变红——双向都拦得住**（既拦"文档改了代码没改"，也拦"代码登记了文档里没有的"）。

### 4.2 契约测试八类（C1~C8）

| # | 文档事实 | 承载文件 | 失败即 |
|---|----------|----------|--------|

| C2 | 11 组状态枚举映射 | `test_enum_mapping.py` + `scan_enum_magic_numbers.py` | 状态机错乱（"10 是待付款还是待发货"） |

### 4.3 三层门禁

| 层 | 触发 | 内容 | 目标 |
|----|------|------|------|
| **L1** | `pre-commit`（本地） | ruff format/check、敏感文件、残留文件、错误码扫描、枚举扫描 | < 5s，违规当场可见 |
| **L2** | PR（GitHub Actions） | `lint` + `contract`（真实 MySQL 8）+ `invariants` + `typecheck`(pyright basic)，由 `gate` job 汇总阻断合并 | < 5min |
| **L3** | merge 到 main | `smoke`：compose 配置可解析（**当前占位**，T1 后替换为"拉起最小档 → 登录 → 下单 → 支付回调"） | < 15min |

APP_ENV=production SECRET_KEY=xxx python -m app.core.config

## 8. 这个仓库最值得学的三个设计

1. **把"约定"翻译成"退出码"**。`gen_data_dictionary.py` 把"表数必须是 38""服务数必须是 9""TASKS 必须是 96 项"这些原本靠人工核对的数字变成了非零退出。文档里还留了**门禁能红的证据**：临时改字段类型、改表头数字，均立即 `exit=1`。
2. **护栏本身要被测试**。`test_startup_assertions.py` 的存在理由是：*护栏自己写错了会安静地不生效，这比没有护栏更危险*。所以每个断言都有正例与反例。
3. **每一步决策都留痕**。"为什么不用 ES""为什么不用物理外键""为什么禁用裸 SHA-256""为什么不把 `docs/sql` 直接挂载""为什么 MinIO 改用 quay.io"——每个"不选"都写清了触发原因。一个"没做什么、因为什么"的记录，比十页"我们做了什么"更有长期价值。

### 9.6 两份 `.env.example` 键名分叉（生产启动风险最高的一条）

`app/core/config.py` 的生产断言要求 `FIELD_ENCRYPT_KEY` / `FIELD_HMAC_KEY` / `ARK_API_KEY`，但**编排层的 `deploy/.env.example` 用的是另一套键名**：

| 语义 | 根 `.env.example`（进程层） | `deploy/.env.example`（编排层） |
|------|------------------------------|--------------------------------|
| 字段加密密钥 | `FIELD_ENCRYPT_KEY` | `MOBILE_AES_KEY` |
| 字段哈希密钥 | `FIELD_HMAC_KEY` | `MOBILE_HMAC_KEY` |
| JWT TTL | `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` | `JWT_ACCESS_EXPIRE_SECONDS` / `JWT_REFRESH_EXPIRE_SECONDS` |
| 内部服务鉴权 | `INTERNAL_SERVICE_TOKEN` / `INTERNAL_SIGN_SECRET` | `INTERNAL_TOKEN` / `INTERNAL_SIGN_KEY` |
| 模型名 | `ARK_MODEL` | `ARK_CHAT_MODEL` |
| MinIO 桶 | `MINIO_BUCKET`（单桶） | `MINIO_BUCKET_PRODUCT` 等 4 个 |
| `SECRET_KEY` | 有 | **无** |

## 附录 A：技术栈沿革（v1.3 移除 Java 的经过）

> 本附录整段为历史/对照说明，按 `docs/tools/gen_data_dictionary.py` 的 `ARCHIVE_HEAD` 规则豁免"去 Java 残留"扫描。

**v1.3（2026-09-21）的核心变更**：后端全栈去 Java，接口契约与业务表**零变化**。

| 决策点 | 结论 |
|--------|------|
| Spring Boot 3.x / MyBatis-Plus | 移除，改为 **FastAPI (Python 3.11+) + SQLAlchemy 2.0 async** |
| Flyway | 改为 **Alembic** |
| Nacos（Spring 生态专属、Java 应用） | **移除**。静态配置走 pydantic-settings（`.env`）；动态配置（AI 阈值等）新增 `sys_config` 表 + Redis 发布订阅热更新 |
| Kafka | **保留**（语言无关），acks=all / 幂等 / DLQ / 本地消息表设计不变 |
| 服务拆分 | 保持 **3 个独立 FastAPI 服务**（主业务 `:8080` / AI `:8000` / Mock `:8081`），故障隔离设计不变 |
| 网关 | Spring Cloud Gateway → 二期改 APISIX / Kong（语言无关） |
| 健康检查 | `/actuator/health` → 统一 `/health` |
| 监控指标 | JVM 指标 → Python 运行时指标（worker 存活、事件循环延迟、RSS） |
| MyBatis-Plus 拦截器（数据权限） | → SQLAlchemy 统一查询过滤器 / Repository 基类强制注入 `user_id` |
| MyBatis TypeHandler（手机号加解密） | → SQLAlchemy TypeDecorator |
| jjwt / Spring Security JWT | → PyJWT + cryptography（RS256 不变；主业务持私钥签发，AI 服务持公钥本地验签） |
| BCrypt（Spring Security） | → 直接用 `bcrypt` 库（passlib 已弃维护） |
| AOP 审计切面 | → FastAPI 依赖注入 + 中间件/装饰器 |

**连带数字变化**：中间件 10 → **9 个**；表 37 → **38**（新增 `sys_config`）；字段 411 → **419**；版本号 PRD v1.2→v1.3、TASKS v2.0→v2.1、schema v1.2、DATA-DICTIONARY/seed/mock_schema 补 v1.1。

**改动施工图**：`.trae/documents/java-to-fastapi-refactor.md`（逐文件改动清单，含 PRD 12 处、TASKS BE 任务措辞等的具体行）。此前的 v1.2 变更则是移除 Elasticsearch、商品搜索改用 MySQL 8 `ngram` 全文索引、撤销 `product.changed` topic、中间件 11 → 10 个。

**为什么这份沿革值得保留**：`docs/VERSIONS.md` §二 #13 专门设了一条"Java 残留 = 0 处活跃引用（仅允许带版本注记的历史/对照说明）"——即**明确允许保留历史对照，但必须带版本注记**。这与"决策留痕"是同一套思路。
